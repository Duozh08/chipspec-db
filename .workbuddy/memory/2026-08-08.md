## 修复识别弹框天选6无法识别
- 根因：站内名 `d.length < 4` 过滤把 `天选6`(3字符) 跳过；OCR 字符级切分 `天 6 选 ...` 产生的 compact token 核心 `天6` 只有 2 字符，又被 `core.length >= 3` 过滤，且 `天6` 不是 `天选6` 的子串。
- 改动 `src/utils/modelMatcher.ts`：
  1. 站内名长度阈值 `d.length < 4` → `< 3`
  2. 型号核心长度阈值 `core.length >= 3` → `>= 2`
  3. 新增 `isApproxSubsequence(a, target, maxSkip=1)` 近似子序列匹配，允许 OCR 字符切分导致单个中文字被拆到后面时仍能命中（如 `天6` 命中 `天选6`）
- 本地测试覆盖：`天选6选哪一个套餐`、`天 6 选 哪 一 个 套 餐 ！`、`华硕天选6游戏本`、`天选 6`、`天选3`、`暗影精灵10` 等均可匹配。
- 已 `git push` 触发 GitHub Actions 部署（提交 170e82c）。

## 第二轮：智能提取型号字符 + 修复待收录重复（提交 6341cd5）
- 用户反馈：①「天选6选哪一个套餐」自主识别仍不匹配（只有删掉"选哪一个套餐"才匹配）；②识别出天选6后待收录列表还提示"天选6"（重复）。
- 改动 `src/utils/modelMatcher.ts`：
  1. 新增 `subsequenceWindow(a, target)`：返回 a 的字符在 target 中按顺序出现的窗口 [start,end]（不要求连续）
  2. `matchLaptopsInText` 新增「全文子序列兜底」：`cleanText = normModel(text)`，对每个站内名 d 检查 `subsequenceWindow(d, cleanText)` 且窗口长度 `<= d.length * 2 + 2` → 命中。覆盖 OCR 在型号字符间插入大量无关文字的场景（如"天选6选哪一个套餐"、"天 选 6 选 哪 一 个 套 餐"）
  3. `extractUnknownCandidates` 常规候选 push 前用 `isKnownVariant` 检查（known.has(name) 或 known 中某项与 name 互相包含），避免"匹配到天选6后又提示天选6待收录"的重复
- 注意事项：全文子序列兜底对 `今天选了6套餐` 这类近似文本也会命中天选6（可接受）；结果按 laptop 去重（matchedIds 集合），每个 laptop 只 push 一次。

## 识别引擎完全本地化，解决语言包下载卡住（提交 4d45af9）
- 问题：tesseract.js 默认从国外 CDN（tessdata.projectnaptha.com / jsdelivr）下载 core + 语言包，国内网络极慢（实测 ~40KB/s，chi_sim 20MB 需 10+ 分钟）导致识别弹框卡在"下载中文语言包"。
- 方案：**识别引擎完全本地化**（public/tessdata/，约 39MB，随站点同源部署，零第三方 CDN 依赖）：
  - `chi_sim.traineddata.gz` (20MB) + `eng.traineddata.gz` (10MB)——从 tessdata.projectnaptha.com 手动下载
  - `tesseract-core-simd.wasm.js/.wasm`——从 node_modules/tesseract.js-core 复制
  - `worker.min.js`——从 node_modules/tesseract.js/dist 复制
- RecognizeModal createWorker 指定 `langPath/corePath/workerPath` 全部指向 `${import.meta.env.BASE_URL}tessdata/`；状态文案改为"加载中文/英文语言模型…首次约需 30MB"
- 注意：① public/ 文件会进 git 仓库（39MB，push 稍慢但一次性）；② 构建后 dist/tessdata 自动包含；③ tesseract.js 有 IndexedDB 缓存，首次加载后自动缓存
- 验证：dev server 下 /chipspec-db/tessdata/worker.min.js 返回 200
